# 好友系统服务端设计文档（S4A21）

## 1. 范围与协议

普通好友由 `Game/Friends/UnitedFriendSystem` 管理，持久化由 `UnitedFriendRepository` 负责。A 添加 B 直接建立 A→B，无需 B 同意；B 的列表不增加 A。删除也仅移除操作者的单向关系。

普通好友与决斗好友协议独立。`REQUEST_ADD_PVP_BUDDY` / `RESPONSE_ADD_PVP_BUDDY` 仅用于决斗好友，不接入普通好友增删流程。

协议名称和编号统一使用 `Network/Core/PacketTypesA21.cs` 中的枚举。包的发送顺序由业务流程规定。

普通好友 ADD、DELETE 的成功 ACK 为 `[result:u8=1]`，失败 ACK 为 `[result:u8=0][error:u8]`。列表和角色身份通过独立通知更新。

## 2. 数据所有权和持久化

- `Friends` 是进程内权威图，以角色名称、Ordinal 大小写敏感方式存储。列表、观察者筛选复用此图，不维护第二份好友缓存。
- `united_friend_relations` 以 `(owner_name, friend_name)` 为主键，含创建时间和 friend_name 反向索引。新库由 `item_schema.sql` 创建，旧库由 v9 迁移创建；禁止运行时隐式建表。
- `RecordFriendship`、`RemoveFriendship` 在同一 Sync 锁内先通过 Repository 提交单边 INSERT/DELETE，再更新内存。单条语句由 SQLite 原子执行；失败时内存不变，不发送成功或列表变化。
- 加载失败不标记为已加载，下一次读取可以重试，不能把读库异常缓存成空图。
- 已有单向边按原样加载，不自动补全反向边；已有双向边视为两个独立关系。超限历史列表不会被截断。
- 角色删除和改名沿用 `HandleCharacterDeletedAsync`、`HandleCharacterRenamedAsync` 维护所有涉及的名字键并通知观察者；改名的两条 UPDATE 在同一事务内提交。

## 3. 普通好友增删

`GameProtocolHandler.RegisterFriendHandlers` 通过 `UnitedFriendSystem.RegisterHandlers` 注册普通 ADD、DELETE 两个命令。解析由 `Network/Parsers/Friends/UnitedFriendRequest` 完成，ACK 由 `Network/Builders/Friends/UnitedFriendPacketBuilder` 构建。

### 3.1 添加

`ADD_UNITED_SERVER_FRIEND` 请求体：

```text
[targetUID:u16][server:u8][nameLength:u32][GBK name]
```

server 当前只支持 1；它不是添加/拒绝操作码。UID 是客户端提示，服务端按精确名称查询当前角色仓储，允许添加真实存在的离线角色，排除已删除角色、自身和不存在的名字。跨频道可添加，不跨独立服务器。

解析拒绝截断、尾随字节、无效 GBK、空白名称、控制字符及不支持的服务器。按普通列表 DSTR 消费边界，名称为 1～255 GBK 字节。只有操作者的列表受 64 个好友上限约束；重复添加幂等，对方的容量不影响添加。

处理顺序：

1. 捕获操作者角色编号、UID、名称，通过既有 `CharacterTransitionCoordinator.RunIfCurrentAsync` 取得角色 gate。
2. gate 内复验目录 session 和捕获身份，拒绝旧连接或同一连接上的旧选角请求。
3. Sync 锁内检查目标、容量，提交 A→B，再更新内存。
4. best-effort 返回公共成功 ACK，然后向 A 发送一份完整列表；同频道在线目标随后补 USERINFO 身份投影。
5. 不给 B 发邀请或列表。ACK/socket 写出失败不回滚已提交关系，重连从持久化状态恢复。

### 3.2 删除

`DELETE_UNITED_SERVER_FRIEND` 的请求是 `[server:u8][name:DSTR]`。UInt32 是名称字节长度，不是角色编号；不得按它查询角色作为容错。

同样通过操作者 transition gate 及身份复验，只移除 A→B，保留 B→A。成功后依次向 A 发送 ACK、subcmd=2 删除通知、subcmd=0 当前完整列表，最后一个好友删除后也发送空列表。删除通知负责清除原生角色实体的好友标记，不能仅用完整列表替代。重复删除返回失败，不影响反向关系。

## 4. 实时投影

### 4.1 完整列表

`NotiPacketTypeA21.UNITED_SERVER_FRIEND_INFO` 的 subcmd=0：

```text
[subcmd:i32=0][count:u32]
N × [server:u8][channel:u16][name:DSTR][level:u8][job:u32]
    [growType:u8][blacklist:u8=0][reserved:i32=0]
```

每个 entry 为 18 字节加名称字节。在线等级/职业/转职从当前会话读取，离线从角色仓储查询；同频道在线 channel=0，异频道在线为真实频道，离线为 0。USERINFO 状态投影保持同频道门禁。

subcmd=0 重建普通好友列表，一次完整快照即可刷新已打开面板，空列表也必须发送。subcmd=2 用于好友删除及角色删除/改名的显式删旧节点并清实体好友位：`[2:i32][count:u32][server:u8][name:DSTR]...`。

运行时统一通过 `SendFriendListAsync` 发送，在 session 的 send lock 内再次校验当前角色编号、UID、名字、目录会话及好友名集合。排队期间关系被删除或会话切换时丢弃旧快照，不能重新显示已删除关系。

新增好友的 USERINFO 身份包同样在 send lock 内复验接收方、目标方的目录 session/角色/UID/名称、频道和关系；目标下线或换选角后不得发送旧实体。删除通知复验接收者身份及该关系仍已删除，避免排队的删除包覆盖重新添加的好友。

初始列表由 `UnitedServerFriendInfoBodyBuilder` 通过已注册的会话构造，与运行时使用同一个 `BuildFriendListBody`。初始化只发送一份完整列表，不由空模板覆盖。

### 4.2 上下线、状态和等级

观察者筛选使用 `IsFriend(观察者, 变化角色)`：A 添加 B 后，A 接收 B 的变化；B 只有自行添加 A 才接收 A 的变化。

- 进入游戏：向观察者发 `INOUT_UNITED_SERVER_FRIEND`；同频道补完整列表，再发 USERINFO，并向登录者投影同频道好友身份。
- 离开游戏：先发上下线通知，再向同频道观察者发 USER_LEAVE。
- 状态变化：通过 `NotifyUserStateChanged` 向同频道观察者推 USERINFO；subtype0 使用当前共享 builder。
- 升级/转职：通过 `NotifyFriendListInfoChanged` 向在线观察者发送当前完整列表，跨频道也更新列表数据。

上下线通知布局为 `[channel:u16][server:u8=1][name:DSTR][blacklist:u8=0]`，离线频道为 0。场景实体只在同频道投影，不能用跨频道 UID 生成实体。

## 5. 测试与验收要求

`--selftest-friends` 串行执行，使用独立临时 SQLite 数据库和本地 socket，恢复全部静态测试状态并清理临时库，不修改运行存档。

自动测试应覆盖单向持久化、迁移、角色删除/改名、协议格式与发送顺序、容量和编码边界、重复/并发请求、离线角色、加载与写入失败、旧会话及排队通知、完整列表和重连恢复。

修改 init 或公共投影后显式设置 `PVF_ARCHIVE_PATH`，串行运行聚焦测试及 `--selftest-all`；最终 Rebuild 必须为 0 warning / 0 error。客户端验收应检查单向增删、删除后重新添加、实时列表与在线图标、跨频道、进出副本以及断线重连后的保存结果。
